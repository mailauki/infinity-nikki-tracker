# Makeup Domain: Tables, Types, and Admin CRUD

**Date:** 2026-08-02
**Status:** Approved, not yet implemented

## Goal

Add a Makeup collection domain to the tracker, modelled on the existing Outfit
domain. Makeup sets have categories, evolutions, an associated outfit set, and
per-user collection tracking. Standalone pieces (variants with no parent set)
are supported, as they are for outfits.

Scope for this spec: database migration, generated + domain types, data hooks,
and admin CRUD. The public `app/makeup/` pages stay on the `ComingSoon` stub.

## Schema

Four new tables and one RPC in the `public` schema. All string foreign keys use
`on update cascade` so renaming a referenced title cascades. All content tables
get RLS with public `select` and admin write via `is_admin()`, plus a
`set_updated_at` trigger.

### `makeup_categories`

Seeded lookup table. IDs are fixed in this order:

| id  | slug           | title          |
| --- | -------------- | -------------- |
| 1   | base-makeup    | Base Makeup    |
| 2   | eyebrows       | Eyebrows       |
| 3   | eyelashes      | Eyelashes      |
| 4   | contact-lenses | Contact Lenses |
| 5   | lips           | Lips           |

Columns: `id`, `slug` (unique), `title`, `image_url`, `created_at`.

Icons for all five slugs already exist at
`public/icons/categories/<slug>.png`; the seed sets `image_url` to those paths.

### `makeup_sets`

One row per makeup _state_, mirroring `outfit_sets` after the evolution merge
(migration `20260622000001`). A base set and each of its evolutions are
separate rows in this table.

```
id            bigint identity primary key
slug          text not null unique
title         text not null
description   text
rarity        int not null
style         text -> styles.title        on update cascade
label         text -> labels.title        on update cascade
seasons       text -> seasons.title       on update cascade
season_category text -> season_categories.title on update cascade
outfit_set    text -> outfit_sets.slug    on update cascade on delete set null
"order"       int not null default 1
base_set      text -> makeup_sets.slug    on update cascade on delete cascade
image_url     text
alt_image_url text
created_at    timestamptz default now()
updated_at    timestamptz default now()
```

**Base vs evolution.** `base_set IS NULL` and `order = 1` identifies a base set.
An evolution is a row with `base_set` pointing at the base set's slug and
`order >= 2`. This is deliberately the same representation used by
`outfit_sets`; the pre-merge separate-child-table pattern is not reintroduced.

**Associated outfit.** `outfit_set` is a nullable FK to `outfit_sets.slug`. It
lives on every `makeup_sets` row, including evolution rows, so a base makeup set
and its evolution can each point at a different outfit state. Because
`outfit_sets` rows _are_ the outfit evolution states, "the makeup evolution
pairs with the order-4 outfit" is expressed by setting the evolution row's
`outfit_set` to that outfit state's slug. `on delete set null` keeps a makeup
set alive if its outfit set is removed.

Title is intentionally **not** unique: evolution subtitles repeat across sets,
the same reason `outfit_sets_title_key` was dropped. Identity is on `slug`.

### `makeup_variants`

```
id             bigint identity primary key
slug           text not null unique
makeup_set     text -> makeup_sets.slug       on update cascade on delete cascade  -- NULLABLE
makeup_category text -> makeup_categories.slug on update cascade
title          text
description    text
rarity         int
style          text -> styles.title  on update cascade
label          text -> labels.title  on update cascade
"default"      boolean not null default false
image_url      text
alt_image_url  text
created_at     timestamptz default now()
updated_at     timestamptz default now()
```

**Standalone pieces.** `makeup_set` is nullable, matching migration
`20260630000001` for `outfit_variants`. A standalone piece carries its own
`rarity` / `style` / `label` / `title` / `description` and has no parent set. The
sentinel-set approach used by `20260702025332` is not used here.

**`default` flag.** A trigger `enforce_base_makeup_variant_default` sets
`"default"` from the parent set's `order = 1`, mirroring
`enforce_base_variant_default`:

```sql
NEW."default" := COALESCE(
  (SELECT s."order" = 1 FROM public.makeup_sets s WHERE s.slug = NEW.makeup_set),
  false
);
```

The `COALESCE` matters: for a standalone piece `makeup_set` is null, so the
subquery returns null and the flag must fall back to `false`. This is the same
correction made for outfits in `20260630072105`.

**Slug format.** `{set}-{category}`, generated by a new `toSlugMakeup()` helper.

### `obtained_makeup`

```
id              bigint identity primary key
user_id         uuid not null -> auth.users(id) on delete cascade
makeup_set      text not null
makeup_category text not null
makeup_variant  text not null
created_at      timestamptz not null default now()
unique (user_id, makeup_set, makeup_category)
```

RLS: public `select` (`true`), plus owner `insert` / `update` / `delete` using
`(select auth.uid()) = user_id` — the same four policies as `obtained_outfit`.

### `toggle_obtained_makeup`

`SECURITY DEFINER`, `SET search_path TO ''`, mirroring `toggle_obtained_outfit`:

```sql
delete from public.obtained_makeup
where user_id = (select auth.uid())
  and makeup_variant = p_makeup_variant;
if not found then
  insert into public.obtained_makeup (user_id, makeup_set, makeup_category, makeup_variant)
  values ((select auth.uid()), p_makeup_set, p_makeup_category, p_makeup_variant);
end if;
```

Deletion keys on `makeup_variant` alone, matching the outfit RPC.

## Types

`lib/types/supabase.ts` is regenerated from the pushed schema, never hand-edited.

New `lib/types/makeup.ts`, derived from `Tables<>` and mirroring
`lib/types/outfit.ts`:

```ts
export type MakeupCategory = Pick<Tables<'makeup_categories'>, 'slug' | 'title' | 'image_url'>

export type MakeupSet = Tables<'makeup_sets'> & {
  makeup_variants: MakeupVariant[]
  makeup_categories: MakeupCategory[]
  evolutions: MakeupEvolution[]
  season: { title: string } | null
  seasonCategory: { title: string } | null
  outfitSet: { slug: string; title: string; image_url: string | null } | null
}

// A makeup evolution is just a makeup_sets row with base_set IS NOT NULL.
export type MakeupEvolution = MakeupSet

export type MakeupSetRaw = Pick<Tables<'makeup_sets'> /* scalar columns */>
export type MakeupVariant = Pick<Tables<'makeup_variants'> /* scalar columns */> & {
  obtained?: boolean
}
export type ObtainedMakeup = Pick<
  Tables<'obtained_makeup'>,
  'id' | 'makeup_set' | 'makeup_category' | 'makeup_variant'
>
```

## Data hooks

Following the `use cache` vs React `cache()` split in CLAUDE.md.

`hooks/data/makeup-categories.ts` — `getMakeupCategories()`. Public lookup:
`use cache` + `cacheLife` + `createPublicClient()`.

`hooks/data/makeup-sets.ts` — `getMakeupSets()`, `getMakeupSet(slug)`,
`getMakeupVariants()`. These read auth-scoped data, so React `cache()`.

`hooks/data/obtained-makeup.ts` — `getObtainedMakeup()`. React `cache()`,
guarded with `if (!user_id) return []` since `getUserID()` returns `null` for
unauthenticated users.

`hooks/data/admin/makeup-sets.ts` and `hooks/data/admin/makeup-variants.ts` —
CRUD mutations. These must **not** be wrapped in `cache()`; a cached mutation
silently no-ops on repeated calls with the same arguments.

`hooks/makeup.ts` — pure transforms, no Supabase access:

- `createMakeupSet()` — resolves a raw row set into a base set with its
  `evolutions` array, using `base_set` / `order`. All base-vs-evolution
  resolution goes through this function; it is never inlined at call sites.
- `updateMakeupVariants()`
- `buildObtainedMakeupKeySet()` / `applyObtainedMakeupKeys()`

`lib/utils.ts` — add `toSlugMakeup(set, category)` beside `toSlugVariant`.

## Admin CRUD

Routes under `app/admin/makeup/`, following the shape of the existing admin
sub-trees. Per the colocation rule, every component below sits beside its
`page.tsx` rather than under `components/`.

```
app/admin/makeup/
  sets/
    page.tsx                  Server Component; Promise.all inside <Suspense>
    loading.tsx
    actions.ts                createMakeupSet / updateMakeupSet / deleteMakeupSet
    makeup-sets-table.tsx     'use client'; owns GridColDef[]
    new/page.tsx
    new/makeup-set-form.tsx
    edit/[slug]/page.tsx
    edit/[slug]/makeup-set-form.tsx
  variants/                   same shape, for makeup_variants
```

Shared DataGrid helpers (`useRowActions`, `LockedCell`) are reused from
`app/admin/eureka/table-utils.tsx` rather than duplicated.

The nav entry is added to `lib/nav-links.tsx` marked `adminOnly`.

### Form behaviour

- **Associated Outfit** — an autocomplete over `outfit_sets` (slug + title) on
  the set form, nullable. Present on evolution rows too.
- **Base vs evolution** — the set form offers "this is an evolution of…",
  selecting a base makeup set; choosing one sets `base_set` and requires an
  `order >= 2`. Base rows leave `base_set` null and `order` at 1.
- **Variant slug** — auto-generated from set + category via `useEffect`,
  read-only until an edit icon unlocks it, matching the eureka and outfit
  variant forms.
- **Standalone pieces** — leaving the set field empty is valid and enables the
  variant's own `rarity` / `style` / `label` fields.

## Out of scope

Deliberately excluded from this spec, to be picked up as follow-up work:

- Public `app/makeup/` pages — the route keeps its `ComingSoon` stub.
- A makeup data provider / context.
- Rendering the makeup association on outfit set detail pages, and the outfit
  association on makeup pages. The `outfit_set` FK is stored and admin-editable
  so this is a straight follow-up.

## Build sequence

1. Write `supabase/migrations/<timestamp>_add_makeup_tables.sql` — one
   migration containing tables, category seed, FKs, RLS policies, triggers, and
   the RPC.
2. `supabase db push --include-all`
3. `supabase gen types typescript --project-id $(cat supabase/.temp/project-ref) > lib/types/supabase.ts`
4. `lib/types/makeup.ts`, `hooks/makeup.ts`, `toSlugMakeup()`
5. `hooks/data/` and `hooks/data/admin/` files
6. Admin routes, tables, forms, nav link
7. `yarn tsc --noEmit` and `yarn lint`

Add new migrations rather than rewriting existing timestamps once a PR is open,
to avoid staling the Supabase preview branch check.

## Verification

The repo has no test suite, so verification is:

- `yarn tsc --noEmit` passes with no errors.
- `yarn lint` passes.
- Manual pass through the admin UI: create a base makeup set with an associated
  outfit, create an evolution of it pointing at a different outfit state, create
  a variant under the base set, and create a standalone variant with no set.
  Confirm the standalone variant saves with `"default" = false` rather than
  erroring on the trigger.

No claim of coverage beyond the above.
